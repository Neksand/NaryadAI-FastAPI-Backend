# AI-исследование: локальная LLM vs детерминированный конвейер

Стенд: Mac M5 Pro, 24 ГБ unified memory, Estimin3n (8,4B, `.hf-cache`), MPS.
Загрузка весов ~19с, генерация ~2с/кейс. Протокол: 40 кейсов (12 good + 12 bad + 8 holdout
вручную написанных, которых нет в тестах) × ru (+holdout × kk), воспроизведение:
`ESTIMIN3N_ENABLED=true ESTIMIN3N_CACHE_DIR=.hf-cache .venv/bin/python scripts/estim_matrix.py`
и `scripts/estim_matrix_v2.py`. Сырые данные: `/tmp/estim_matrix.json`, `/tmp/estim_matrix_v2.json`.

## Результаты

| Система | Верные | Найдено плохих | Ложные доработки |
| --- | --- | --- | --- |
| Mock-конвейер (правила, 67 тестов) | 100% (64/64) | 100% (32/32) | 0% |
| Estimin3n v1 (мягкий промпт) | 52,5% (21/40) | FAIL 2/12, REVIEW 1/8 | 0% (всё PASS) |
| Estimin3n v2 (строгий промпт с критериями) | 22,5% (9/40) | FAIL 0/12 | 75% (15/20 хороших в REVIEW) |

## Вывод (честный)

1. Сырая малая LLM хрупка к промпту: v1 льстит (почти всё PASS),
   v2 придирается (27 REVIEW из 40, ноль FAIL). Качели 52,5% ↔ 22,5% на тех же кейсах.
2. Поэтому архитектура «правила → LLM → пост-правила»: обязательные требования проверяет код
   (100% детерминированно, 0 дисперсии, мс, $0), LLM — только советчик с объяснением.
3. Напрямую несопоставимо с бенчмарками больших моделей на GPU (другой вес — 8B локально,
   другая методика). Наше утверждение уже: конвейер не может пропустить
   плохой отчёт по обязательным полям — это свойство кода, а не статистика.

## Границы

- Выборка мала (40), языки — ru + 8 kk; Kazakh-специфика отдельно не мерялась.
- Замерялась text-ветка; vision/audio Estimin3n не гонялись.
- Латентность MPS на ноутбуке, не прод-GPU.
